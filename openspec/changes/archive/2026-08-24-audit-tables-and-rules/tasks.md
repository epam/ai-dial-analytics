## 2. Schema migration

- [x] 2.1 Read the live DDL of `table_definition` and `column_mapping` as it stands after `V26`
      (`V25__denormalize_table_catalog` added `grain_key TEXT` and `ordering_key TEXT[] NOT NULL
      DEFAULT '{}'` and dropped `enrichment_grain` / `table_ordering_key`) and record each column's
      exact physical type
- [x] 2.2 Write `src/main/resources/db/migration/postgres/V27__audit_trail.sql` — `V25` and `V26` are
      taken on the default branch — creating `revinfo` (`id INTEGER GENERATED BY DEFAULT AS IDENTITY
      PRIMARY KEY`, `timestamp BIGINT NOT NULL`, `author VARCHAR(255)`, `email VARCHAR(320)`)
- [x] 2.3 Add the two `*_aud` tables to `V27` — `table_definition_aud` and `column_mapping_aud` —
      each mirroring its live table's column types (`jsonb` and `text[]` preserved, so
      `table_definition_aud` carries `ordering_key text[]`, `tag_order text[]`, `access jsonb`, and
      `grain_key text`; `column_mapping_aud` carries `element_type`), plus `rev INTEGER NOT NULL` FK
      to `revinfo(id)`, `revtype SMALLINT`, and `PRIMARY KEY (rev, <live pk columns>)`
- [x] 2.4 **Every audited non-id column in every `*_aud` table must be nullable**, including those
      that are `NOT NULL` in the live table — a delete row writes NULL into all of them, so a
      `NOT NULL` here breaks every delete of that entity at commit time. `ordering_key` is the newest
      instance of this trap (live: `NOT NULL DEFAULT '{}'`); `write_mode`, `system`, and `access` are
      the others
- [x] 2.5 Carry over neither the live tables' foreign keys (only `rev → revinfo(id)` remains, so a
      delete in a referenced table cannot cascade away audit history) nor their CHECK constraints —
      `grain_key_only_on_enrichment` must not be mirrored, since a delete row nulls both columns it
      relates
- [x] 2.6 Add `audit_activity` to `V27` (`activity_id VARCHAR(36)` PK, `activity_type`,
      `resource_type`, `resource_id`, `epoch_timestamp_ms BIGINT`, `initiated_author`,
      `initiated_email`, `parent_activity_id VARCHAR(36)` nullable, `revision INTEGER` FK to
      `revinfo(id)`) with indexes on `(resource_type, resource_id)`, `epoch_timestamp_ms`, and
      `parent_activity_id`
- [x] 2.7 Confirm `column_mapping_aud` carries both id components as **plain columns with the live
      names** (Envers' `originalId` is a mapping-level name that never appears in SQL — there is no
      `original_id` prefix)

## 3. Audit persistence layer

- [x] 3.1 Create `service/audit/ActivityType` (`Create`, `Update`, `Delete`) and
      `service/audit/ActivityResourceType` (`Table`, `TableColumn`) — constants
      spelled exactly as the wire values; add a class comment recording that this deliberately
      departs from ADAS's uppercase-constant convention for frontend compatibility
- [x] 3.2 Create `AuditRevisionEntity` (`@RevisionEntity(AuditRevisionListener.class)`, table
      `revinfo`, `@RevisionNumber` id with `GenerationType.IDENTITY`, `@RevisionTimestamp`
      timestamp, author, email, `@OneToMany(cascade = ALL, mappedBy = "revision")` activities)
- [x] 3.3 Create `AuditActivityEntity` (table `audit_activity`, `UUID` id mapped
      `@JdbcTypeCode(SqlTypes.VARCHAR)` and generated as UUIDv7 via
      `UuidCreator.getTimeOrderedEpoch()`, string-enumerated type columns, nullable
      `parentActivityId`, `@ManyToOne` back-reference to `AuditRevisionEntity` named `revision`)
- [x] 3.4 Create `AuditResourceMapper` translating a changed entity class + id to
      `(ActivityResourceType, resourceId)` — `TableDefinitionEntity`→`Table` and
      `ColumnMappingEntity`→`TableColumn` as `<tableName>:<sourceName>` — returning empty for
      anything unmapped, and translating Envers `RevisionType` to `ActivityType`
- [x] 3.5 Create `AuditRevisionListener implements EntityTrackingRevisionListener`: `newRevision`
      stamps author/email from `SecurityClaimsExtractor` (falling back to `unknown` with a null
      email, and never propagating an extraction failure to the caller) and the timestamp;
      `entityChanged` appends a deduplicated activity to the revision's collection
- [x] 3.6 Implement dedup inside `entityChanged` against the revision's own activity collection —
      one entry per `(resourceType, resourceId)`, with `Create`/`Delete` replacing a recorded
      `Update` and a later `Update` never replacing anything (no `ThreadLocal`)
- [x] 3.7 Implement bidirectional parent linking in the same pass: a new `TableColumn` activity adopts
      the `Table` activity already present for its table, and a new `Table` activity back-fills the
      parentless children already recorded for it — Envers gives no ordering guarantee, so neither
      direction may be assumed
- [x] 3.8 Give the listener its collaborators without a static, so several Spring contexts in one JVM
      — as cached test contexts are — stay isolated. **Implemented differently from the original plan**:
      `ApplicationContextAware` instance fields cannot work, because an object Envers creates
      reflectively has no channel to Spring at all, and the only channel that would work is the static
      holder this task exists to avoid. Enabling `hibernate.cdi.extensions` (1.3) instead makes Envers
      resolve the listener as a Spring bean with ordinary constructor injection — no static, and each
      context wires its own instance
- [x] 3.9 Annotate `TableDefinitionEntity` and `ColumnMappingEntity` with `@Audited` — these are the
      only two entities left behind the table catalog after the `V25` denormalization. Do **not**
      annotate `RuleEntity`, `EvaluatorEntity`, `EvaluatorVersionEntity`, `PipelineEntity`, or
      `SavedQueryEntity` — each is deliberately excluded (see `proposal.md`)
- [x] 3.10 Make dependent deletes visible to Envers: in `TableCatalogService.delete()`, remove the
      columns explicitly through their repository (`columns.deleteByTableName(name)`) before
      `definitions.delete(entity)`, because the current `ON DELETE CASCADE` fires no Hibernate event
      and would leave the deletions unrecorded. Use the derived `deleteBy…` method (it loads and
      deletes per entity); do **not** use a `@Modifying` bulk query, which bypasses Envers. Leave the
      database cascade in place as a backstop. The grain and ordering key need nothing — they are
      columns of the definition row and go with its own `Delete`
- [x] 3.11 Confirm no other `ON DELETE CASCADE` reaches an audited table unnoticed, and record the
      finding. `rule.target_enrichment` cascades from `table_definition` but rules are not audited
      here, so nothing is lost today — note it as a hole to close when rules are added.
      `rule.source_table` (`V26`) is `RESTRICT` and pre-checked with a 409, so it is not one
- [x] 3.12 Leave `CatalogSchemaWriter.replaceColumns` as delete-all-then-insert-all, and record why in
      a comment. **This task's premise was half wrong, settled by test rather than argument**:
      `AuditProcess.addWorkUnit` merges work units per `(entityName, id)` within a revision, so the
      feared `_aud` primary-key collision cannot happen — but the merge yields a `ModWorkUnit` even for
      an identical re-insert, so a re-post *does* report every column it re-states. A reconciling
      rewrite was implemented and then reverted: it regresses the case where two columns swap exposed
      names (violates `exposed_name_unique_per_table` mid-flush, which deleting both first does not),
      which is a worse failure than a coarse feed entry on a rare admin path. The over-reporting is
      now stated in the spec instead of being papered over; 8.8a pins both legs

- [x] 8.7 Integration-test the activity grain end to end: a table create produces one `Table`

- [x] 8.8a Integration-test the delete-then-reinsert of one column id in a single transaction — the

      and (the pessimistic leg) an identical re-insert still writes an `Update`, so the limit is
      asserted rather than assumed. Also asserted: an ordinary re-save of unchanged values writes
      nothing, because Hibernate's dirty checking never reaches Envers
- [x] 8.8b Integration-test a column rename: a `Delete` for the old `<table>:<oldName>` and a `Create`
